# Frontend UI (`src/`)

Conventions for everything rendered under `src/` — colors, the design system, and user-visible copy. Moved here from the root `CLAUDE.md` so they load when you work on the UI.

**Colors.** UI: Tailwind classes / CSS variables, don't hardcode hex — and an arbitrary-value class is the same hex under another spelling: `bg-[#35302b]` *is* `bg-surface-raised`, and the `src/app.css` ramp exists to end exactly that drift (its comment lists the near-identical shades it absorbed). A brand color the palette can't express — Discord blurple — is the standing exception, and carries its reason in a comment. Charts: `import { CHART_THEME, getSeriesColor } from "$lib/config"` and color categorical series via `getSeriesColor(i)` — `getChartColor(i)` is the *civilization fallback* ramp, not a rotation. Nation/civ: `getNationColor` / `getCivilizationColor` / `getNationChartColor` from `$lib/config` (e.g. `getCivilizationColor(player.nation) ?? getChartColor(i)`). Reference: `docs/reference/color-scheme.md`.

**Design system.** The app has one, in code rather than prose: the `--color-surface` ladder in `src/app.css` — `surface-deep`, `surface-sunken`, the base `surface` a `Panel` sits on, `surface-raised`, each with its `-hover` step — whose comments say what every level is for. `Panel` (`$lib/ui/Panel.svelte`) is a `bg-surface` card with an `h2` title at `text-base`; `PanelInset` (`$lib/ui/PanelInset.svelte`) is the *recessed* `bg-surface-deep` box inside it, the step below the panel's surface, with an optional `h3` label. (`$lib/ui` is a directory — import the component file.) That pair is the home page's shape. Match the surfaces around you before inventing a layout — an `<h2>` in game detail is `text-lg`, while `Panel`'s own title is `text-base`; a disclosure is the chevron-with-`rotate-90` idiom; a scroll container takes no markup of its own — the 5px tan scrollbar is global (the `::-webkit-scrollbar` rules in `src/app.css`, marked `data-scrolling` by `markScrolling` from `$lib/scroll-activity`, wired once in the root layout), so a per-container scrollbar class or action is a regression and `scrollbar-gutter: stable` is the only thing still set per container (`.view-scroll`, `.profile-scroll`); a profile link goes through `ProfileLink`. A segmented switch has two shapes here and the neighbouring surface decides which: the lit-thumb control — an equal-column grid with a raised-surface thumb translated by the active index — which is now two shared components and **not** something to hand-roll a ninth time, and a thumbless bits-ui `ToggleGroup` styled with `data-[state=on]:bg-surface-raised` (`SpecialistsTab.svelte`, and the Yields toggle in `YieldsStatsPanel.svelte` it was copied from). The lit-thumb pair splits on semantics, not looks: `SegmentedNav` (`$lib/ui/SegmentedNav.svelte`) for cross-route **links**, carrying `aria-current` (`TournamentViewTabs.svelte`, a game's Analysis/Map toggle in `GameHeader.svelte`); `SegmentedSwitch` (`$lib/ui/SegmentedSwitch.svelte`) for in-page **buttons** that toggle a view of the route you are on, carrying `aria-pressed` (game detail's science (`TechsTab.svelte`) and empire (`EconomyTab.svelte`) switches and the Events tab's Events / Map Pins switch (`EventsTab.svelte`), the tournament matches page's view toggle and stats page's status switch, the `/players` board switch, and the stats catalog's Leaders band switch). Its `borderShade` is the one choice the caller still makes, and the neighbouring surface makes it: `sunken` against a `bg-surface` card, `surface` against anything raised. The one lit-thumb control still hand-rolled is the tournament overview's championship and per-division toggles — a bits-ui `Tabs.List` that also owns the fading panel beneath it, so its rail is markup on a tablist rather than a group of buttons. Match whichever one is beside you, and make the next copy of the `ToggleGroup` shape its own extraction. An on/off *preference* is a third thing and not a segmented switch at all — `role="switch"` with `aria-checked`, rendered through one shared row, as the account page does. Reserve the slot for an icon that may not resolve: `SpriteIcon` renders *nothing* when `getSpritePath` returns null, which is every sprite, so the glyph goes in a fixed-size wrapper the way `BuildComparison.svelte` does (`<span class="flex w-3.5 flex-none">`) or the row unaligns. Reserve the height for a row count that varies, so a panel doesn't resize under the pointer. Prefer Old World's own glyph to a hand-rolled SVG or an emoji — `SPRITE_MANIFEST` (`$lib/generated/sprite-manifest`), through `getSpritePath`, is what says whether the game ships one.

**Copy.** A heading names what is on screen, not the machinery behind it — "Turn summary", not "Logged this window". Use the game's own string where it has one, and note there are two different sources: UI strings live in `Reference/XML/Infos/text-ui.xml` ("Turn summary" is its `TEXT_UI_EVENT_LOG_TURN_SUMMARY`), while the baked tables in `src/lib/generated/` hold *entity* names. Reach for a baked name through the wrapper that already does the lookup rather than writing another `?? formatEnum(...)` inline: `nationName`, `civilizationName`, `characterName`, `cognomenName` (`$lib/utils/formatting`), `techName`, `improvementDisplayName`, `projectDisplayName` (`$lib/game-detail/helpers`), `specialistName` (`$lib/game-detail/specialists`). `civilizationName` is the one for a value that can be a nation OR a tribe — a city's holder, a unit's owner — and `cityOwner`/`unitOwner` (`$lib/game-detail/helpers`) wrap it again with that holder's crest key and colour. Where no wrapper exists the table may not either — units, resources and families have no name table at all and still differ from the enum — and a wrapper can live outside both modules above: `specialistName` wraps a `name` field in `generated/specialists.ts`, which is not a `*-names` module, and `formatEnum()` over the same zType silently collapses the three urban tiers into one name. Check before asserting `formatEnum()` is correct for a noun. Don't caption an interaction the UI already affords. A tooltip claims only what the data supports. A confirm dialog for something irreversible says so.
